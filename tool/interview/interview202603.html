            # 如何设计一个AI Agent？

            我先简单介绍下这个项目的背景，背景就是当时我们的运营团队每天会处理大量重复的工单，比如：优惠券该如何使用？新人福利如何获取？订单咨询等问题，所以想做一个能智能处理这些工单的AI客服Agent，主要是想有 能对工单进行分类、RAG知识库检索、自动生成草稿回复 这些功能；

            之后跟产品沟通后，我们这个客服Agent的核心工作链路主要是 工单入库、工单分类、知识库检索、草稿生成、人工审批、发送，这样一个工作流程；主要是承接我们C端用户和部门内其他平台的运营类工单查询；所以当时我们对这个Agent的定位就是一个知识库量级在千级文档以内的单Agent项目，主要面对的是"事实型问答"，更需要的是"准确的事实信息"，而不是"复杂的操作流程"。

            在技术方案设计之前，我们也调研了目前市面上比较成熟的Agent项目；其实广泛意义上来讲，我觉得所有围绕大模型做的应用都可以算是Agent；包括ChatGPT、DeepSeek官网这种带有联网搜索功能的大模型调用是比较简单的Agent项目，像Claude Code、Codex、Trae、Cursor等等这些AI代码编辑工具，之前比较火的OpenClaw，Manus这些算是设计比较复杂的Agent项目；目前Agent这个行业也是处于一个快速迭代的时候，没有哪个Agent工具可以说能够解决所有的业务问题；而且我觉得Agent的底层原理其实不是新的东西，基本都是围绕大模型搭建的一套工程化的体系，就看这套工程适不适合自己的业务场景了；所以调研到最后，我们决定不直接使用其他像LangChain这种比较成熟的第三方框架，直接基于我们智能客服的场景自研搭建一套Agent；

            目前市面上的Agent框架很多，但分析后发现其实底层的Agent结构基本都差不多，基本都是包括 上下文管理、工具系统、任务编排设计、状态和记忆、评估和观测、约束和恢复，主要是这六个模块，如果是多Agent项目还会设计Agent之间的协作；因为我们这是一个单Agent项目，就先不考虑多Agent之间的协作，所以我们从一开始设计的时候，就主要从刚才说的这六个模块去考虑，后续再做多Agent协作的升级；所以在前期我们会花比较多的时间去进行整个Agent协议数据模型的设计，这一块也是我们整个Agent项目最重要的部分；因为这一部分的设计关系到整个Agent项目的稳定性以及后续的迭代和升级；

            我们的Agent协议的数据模型是围绕 从用户提交一个工单开始，到工单任务结束 整个生命周期来设计的。 当用户创建一个工单，我们会创建一个工单的长期上下文，就类似于ChatGpt中的某个单独的聊天框，这个工单上下文会跟用户id和工单id进行关联，我们叫thread对象，也可以叫session对象；它会包含这个工单的内容、主题、分类、用户ID等字段信息； 在当前工单上下文中发起一次对话会我们创建一个run对象，也可以叫做任务对象，它主要存的是某一轮对话任务的具体执行信息，它会包含当前轮次对话的任务状态、对话内容等信息； 而在每一轮对话中，在我们Agent后台其实是会执行多少步骤，比如工单分类、知识库检索、草稿生成等等，它主要存的就是每个step里面执行信息，比如模型调用情况，token消耗、耗时等等； 而每一个步骤又会有多个事件流类型，比如任务创建、步骤创建、步骤完成、草稿已生成、任务结束、任务失败等等，它其实是对应的整个Agent生命周期中各种不同类型的事件处理；它里面主要存的是当前事件类型、error信息，以及来源run_id和step_id； 所以从数据模型的层级关系来区分的话，用户创建一个工单会生成一个工单上下文，单个工单上下文会有多个对话任务，单个对话任务有多个step，而单个step又有多个事件流；除此之外，在单个对话任务中的每个step结束后我们都会生成一份Checkpoint快照信息，和artifact产物信息，这样就基本能覆盖从工单创建到工单结束所有的数据状态的管理；有了这些数据之后，我们就可以对Agent执行链路的整个生命周期进行观测和评测，也是方便后续迭代优化可以有比较准确和详细的数据做支撑；

            数据模型设计完之后，在数据分层的设计上，我们单独设计一个store模块用于数据的持久化，它主要封装对sql数据库的调用，上面说的所有数据模型的读写操作都通过store模块暴露出来的方法进行调用； 同时我们也会有单独的model层用于对大模型调用的封装，单独的事件管道用于事件的写入和SSE流式事件的封装，也会封装取消信号总线，用于广播取消信号；封装RAG知识库的处理；会单独封装skill层用于skill的注册；

            除此之外，我们也会单独封装Agent的runtime用于整个Agent系统的任务编排，runtime算是我们整个Agent设计最核心的部分了，刚才说的数据模型和数据分层模块最终都会归拢到runtime里进行调用，我们Agent的主要执行链路也是在这里进行编排：从接收一个对话任务，到驱动大模型进行推理，调用skill，写入step信息，检查是否需要人工审查，写入Checkpoint快照信息，循环执行不同步骤，直到对话任务完成，都是在runtime也进行设计；

            之后在整个node服务启动的时候，我们会完成上述所有模块的初始化，同时也会将初始化之后的各个模块传入我们Agent的runtime里面，方便后续进行任务编排的时候进行调用；

            总的来说，在我们上线的第一版本中，客服工单的处理是线性管道：分类→检索→起草→审批；Agent的任务编排逻辑就是：接受到一个对话任务，创建Thread对象、Run对象，之后通过编排层模型判断应该调哪个skill，同时要求模型返回约定的json，Agent拿到模型返回的json，取调对应skill的excute方法，执行对应skill代码逻辑；直到所有步骤都执行完毕，等待前端人工审核；审核完毕，整个对话任务执行结束。后续用户发起新对话会带上当前工单id、thread_id，重新走刚才的对话任务执行流程。

            而且现在所有的数据都通过sql落库，用户每一轮的对话信息都可以在我们的B端监控平台查到，同时我们也按照我们设计的数据模型，在B端监控平台建立了一套可视化的分析工具，用于查看用户任意时间节点的对话内容信息；

            # 如何设计一个B端低码平台？

            简单说下项目背景，因为在团队内存在很多B端平台，运营平台、打断平台、运力平台、云控平台 等等，其他大多数平台页面基本都是CRUD类的增删改查页面，里面的页面结构基本都大多类似，表单字段的提交校验，table列表的查询；而且我们团队现在这些平台技术栈都是React，用的组件库基本都是ant-design，UI风格基本一致；在之前开发模式基本都是复制粘贴一个旧页面，然后改一改；这样时间长了后项目体积就比较臃肿，里面基本都是相似的代码不停重复。

            基于这样一个背景，我们就想搭建一个可以快速产出B端CRUD页面的B端低码平台，方便开发、产品或运营可以快速搭建比较常规的B端页面。

            这个项目整体是一个React + Node.js 的全栈项目，项目整体的分层架构设计从客户端到服务端分别是：视图层、协议层、物料层、基础能力、和后端服务； 视图层的就是B端页面的编辑端和展示端，也是用户直接能看到的部分，目前包含的模块主要是可视化拖拽和编辑、画布渲染、属性面板配置和页面展示这些； 协议层是整个项目最重要的部分吧，它主要是包含了渲染引擎、JSON Schema设计、事件流配置、变量系统、接口数据源管理、组件树设计，状态与数据流管理等等； 物料层就是整个平台提供的组件物料和页面模板，主要包含像input输入框、select下拉组件这一类通用的基础组件，包含筛选查询和列表展示的高级组件，还有一些业务组件和页面模板； 基础能力就是主要是权限管理、版本管理、发布机制、CI/CD工程化，这些围绕这个低码平台生在生产环境运行的底层配置； 后端服务就是整个低码平台的后端接口服务，它主要包含页面的创建、编辑、查询、展示、发布、回滚等接口，还有其他的 数据库、接口代理、jwt鉴权、这些

            整体项目架构是用monorepo搭建的一个单仓库多模块的项目，编辑端和展示端是两个 Vite + React 的前端项目，编辑端通过 Zustand+immer 统计进行数据状态管理；组件物料底层还是用的antd-design，然后这个组件库基础上做二次封装，后端通过 koa + mysql 搭建；

            整个平台设计过程中第一个比较核心也是比较基础的地方就是 JSON Schema 的设计；这里我是用一个大的pageData来完整的描述整个页面，里面通过config存全局配置，里面会有页面属性、样式等信息；也通过api保存接口管理、variable保存变量配置、events存事件流配置；除此之外还有elements保存整个页面的组件树结构，同时也会有一个elementsMap保存扁平化组件配置映射信息，这算是一种双轨制的数据模型设计吧：elements 只存组件id 和 它的parentId，保存的是整个页面的组件布局结构，elementsMap则扁平化的保存所有组件的配置信息，渲染的时候通过组件id索引获取信息进行渲染；

            另一个比较重要的部分就是渲染引擎的设计；首先我们把渲染引擎单独抽成一个共享包，editor 编辑预览和web生产环境对外展示的时候用的是同一份代码同一个 store 定义；渲染引擎本质就是对 elements 树做一层层递归懒加载，并注入合并好的 props/events/api；对于增删改查等操作是通过设计一套事件流来进行管理编排，用户在某一行点击的行为背后挂的其实是一棵事件行为有向无环（DAG）图，里面有发请求、弹确认框、刷新表格、跳链接等等二十多种原子动作，最后会被转成链表顺序串起来执行；

            对于后端的设计，就是通过 router/controller/service 三层来进行分层管理，MySQL 存的 pageData 就是一个 LONGTEXT 字符串，可以发布快照保留最近三个版本，也提供一键回滚功能；在低码平台中后端角色就是提供数据的存取服务，更多的复杂逻辑其实是在前端；

            # 电商平台从商品展示到售后，如何进行设计？

            电商C端从商品展示到下单、支付、售后 算是所有电商业务中比较核心的模块了吧，基本上只要做电商的都会搭建这样一套业务流程；不管是之前接触的在线教育、日化用品、零售、还是现在的打车，虽然业务形态都不一样，但其实底层的技术设计逻辑都比较类似；基本就是两方面：一个是比较良好的用户体验、一个是安全稳定的交易链路；基本上百分之80左右的研发设计都是围绕这两点去做的；

            先从用户体验上来说吧，电商 C 端的用户体验本质上就是一件事：用户永远不能看到白屏，并且永远有反馈。像商品首页这种包含轮播图、推荐位、商品列表、秒杀入口、分类导航的多模块页面，核心思路基本都是围绕“动静分离、分级加载”这个方向去优化。能静态化的一律推到CDN，用户打开瞬间就有内容，接口全挂了也不会白屏。首先是静态骨架屏的展示，之后再是动态数据的加载，动态数据按优先级分P0、P1、P2：P0是首屏必须的，比如轮播图、秒杀入口，资源请求最好聚合为一个接口，因为需要考虑弱网多个http请求的往返时间；P1像商品列表，滚到才加载,还有比如秒杀倒计时启动；P2像个性化推荐、分类导航、埋点这些，空闲再加载。还有像商品都会有很多图片，能用WebP就用webP、低清图占位，固定宽高比防止布局抖动、首屏图预加载、其他不需要首次展示的懒加载。二次进入直接走Service Worker缓存，秒开。还有就是弱网分级处理：弱网下强制接口聚合、图片降清晰度、关闭动效，断网展示离线缓存。 用户体验指标量化上，我们会用按网络和机型分桶，看75分位和90分位的数据，目标就是：正常网络下首页 FCP 小于 1s、LCP 小于 2 秒，弱网 4G 下 LCP P75 小于 3 秒，二次进入小于 300 毫秒。

            另一个比较重要的模块是秒杀，秒杀业务比较重要的问题就是：倒计时要准、按钮要防重、流量要削峰。倒计时的时间是从服务端拿权威时间算offset，再用performance.now()这种单调时钟来走，这样用户改时间、浏览器休眠都不影响，还有就是客户端倒计时归零不等于能下单，能不能抢永远以服务端时间窗、资格令牌、库存为准；dom更新上用requestAnimationFrame替代定时器进行更新；按钮防重上我不会在按钮上加防抖，因为这样会吃掉用户的合法重试操作，我会用状态锁加幂等Key，点击瞬间按钮锁死，同时生成一个UUID，同一次操作的重试复用同一个Key，后端碰到重复Key直接返回第一次的结果。既防了连点，又不误伤正常重试。 秒杀抢购的瞬间可能会出现用户疯狂连点的情况，这时会出现瞬时的流量高并发，流量削峰主要是后端做并发限制，但前端也可以配置做一些处理，我们会在开抢前一两分钟预发资格令牌，没令牌的请求网关直接拦；抢购先进排队，SSE 叫号，把洪峰变成可控的流；同时对于请求失败的情况，用户也可能会不停点击重试，前端会通过随机抖动来分散重试时接口的压力； 下单同样也是需要幂等，除此之外下单成功锁库存，给订单30分钟有效期，前端配合支付倒计时，超时自动关单释放库存，防止库存被死锁。

            还有一个最重要的模块就是支付，支付核心要解决的问题就是：防重复扣款，和超时后的最终一致；防重复扣款通过双Token机制解决：前端幂等Key解决重复提交，后端一次性payToken绑定用户、订单、渠道，解决请求合法性；还有就是超时处理，前端超时一律进入UNKNOWN状态，UI显示"支付处理中"，然后靠持续查单收敛，轮询订单状态接口直到拿到成功或失败；当前后端也需要做一些处理，比如支付单要有事实记录，定时扫描处理太久的单去主动查三方，还有每日对账这些；支付链路我们会维护一个完整状态机：未发起、创建支付、排队、拉起收银台、处理中、成功、失败、取消，加上 UNKNOWN，后端会在高峰期先把支付单入队，叫号再拉收银台。总的来讲，就是幂等提交、后端有事实源、前端超时只认处理中、靠查单收敛终态。

            整个电商从商品展示到支付售后比较核心的设计要点就是：用户永远不能看到白屏、服务端才是唯一的事实源、交易操作必须幂等。体验靠分层加载和弱网分级量化到 FCP、LCP；交易用状态机；秒杀抓倒计时、防重、削峰；支付抓双 Token 和查单收敛。

            • 弱网分级处理：图片低清、接口聚合、关闭动效

            # 高精地图页面经过多次绘制后，再拖拽页面重新请求接口数据，重新绘制时，就会出现页面卡顿的情况，怎么进行渲染性能优化？

            ai生成

            先交代背景。我们地图上要渲染车道级高精数据——每条车道线、每个道路边界，都是几百上千个坐标点。用户的实际体感是什么呢？页面多次绘制之后，再拖一次地图，就会明显卡一下，严重的时候要卡好几秒。

            当时我第一反应是：*卡在哪里？*我没有直接猜，而是先加了埋点，把渲染拆成"本地转换"和"mapvgl 绘制"两段，分别计时。测出来的结果很直观：一次渲染，本地转换只占 2% 到 5%，剩下 95% 以上全耗在 mapvgl 的 setData 上，一次就要 3.7 秒，多的时候能到 20 秒。

            那为什么 setData 这么贵？查了官方文档，这是 mapvgl 的设计约束：它没有增量接口，你要往里加数据，只能把"历史全部加新增"整份重传。我们实测下来，大概每条数据 5 微秒。听起来不多，但一次要重传几十万条，就是秒级了。

            更关键的发现是：我们当时是每个瓦片、每个类型都做一次全量重传——同样一批数据，被重复处理了十二倍。打个比方，就像搬家，本来一车能拉完的箱子，我们来回拉了十二趟。

            所以根因用一句话总结：耗时等于数据量乘以单价，而我们的数据量被重复放大了十几倍，而且只增不减——拖得越多，历史数据越多，每次重传就越贵。

            基于这个结论，我们做了四件事。

            *第一，聚合。*把一轮请求里的所有瓦片，先按类型归并，每个类型只提交一次。这一步直接把处理量从 76 万条降到了 4.4 万条。

            *第二，分帧。*所有对图层的写入，不再一次性同步做完，而是拆成小任务放到 requestAnimationFrame 里，每帧最多干 8 毫秒，干不完下一帧继续。这样哪怕总量要一秒多，主线程也永远有空隙响应拖拽——地图上看到的效果是"逐渐画出来"，而不是"卡完一下全出来"。

            *第三，限界。*单个类型的数据量大了，单次提交还是会超时，所以把每个类型拆成 3000 条一个子层，超出就开新层，保证单次操作的耗时封顶在二三十毫秒。

            *第四，砍掉重复操作。*图层显隐切换原来每次都要遍历全部图层刷一遍，加了个缓存，状态没变就跳过。

            效果怎么样？几个数：单帧最大耗时从 120 到 165 毫秒，降到 33 到 36 毫秒，已经低于浏览器"长任务"的 50 毫秒阈值；图层切换从 300 多毫秒降到接近零；主线程从"一次冻结好几秒"变成"完全感觉不到"。

            最后说两句实话。第一，我们做的是"减少次数、限制规模、改变形态"，但 mapvgl 全量替换的单价消不掉，所以还有一道天花板：拖得越远，累计数据越多，重传量就越大——要彻底解决，只能靠后端减量，比如按缩放级别抽稀、只返回视口内的数据，这是我们下一步的方向。第二，整个过程里，所有结论都是先量化、再动手，中间也踩过坑、回退过方案，但原则没变：基于数据，不猜。

            为什么mapvgl只有全量方法，没有提供增量绘制的方法呢，这是出于什么考虑呢？

            这个问题我先直接给结论：这不是 mapvgl 能力上的缺失，而是 API 设计上的取舍——它选择了"简单可控"，放弃了"极致性能"。可以从三个层面理解。

            *第一层，是它的设计哲学。*mapvgl 采用的是"声明式"模型，跟 React 类似：你负责维护状态、把完整的数据交给它，至于怎么渲染、怎么更新，是它内部的事。React 里我们写 setState，也不会去手动 diff 每个节点对不反对吧？mapvgl 的 setData 就是同一个角色——你给它完整状态，它来负责重建。但是这个模型天生的一个代价就是：没有增量的入口——因为库不会去追踪"哪一条数据是新增的、哪一条是删除的"。

            第二层，是增量实现的真实成本。如果要做增量接口，mapvgl 内部就必须维护一张"数据项和渲染对象的映射表"——每一条数据对应哪个顶点缓冲、哪个 mesh。一旦支持增删改，就要处理：数组插入后所有索引的漂移、包围盒要重新计算、点击拾取的命中编号会变……这些全是牵一发动全身的活，实现复杂度比"全量重建"高一个量级，而且很容易出 bug。对库的维护者来说，这个性价比不划算。

            *第三层，是场景匹配度。*地图瓦片的使用模式是什么？一次请求、批量加载——我拖一下地图，后端给我几万条数据，我一次性提交进去。在这种场景下，全量替换的代价是可控的。而增量接口真正的价值场景是"高频、单条修改"——比如一个实时数据看板，每秒更新一条。但那是图表库的活，不是地图渲染的主链路。mapvgl 是为"批量加载"优化的，不是为"单条编辑"优化的。

            当然，它也不是完全没有轻量操作——setOptions 改样式、show/hide 显隐、clear 清空，这些都是轻量的，缺的只是"数据级"的增量。

            所以回到我们项目的应对思路就很清晰了：既然全量替换消不掉，我们就从三头下手——把全量次数压到最低（聚合）、把单次规模限住（子层化）、把执行摊进多帧（时间切片）——在框架的约束下，把性能挖到极限。

            # SSR渲染为什么会缩短白屏时间，它相较于CSR最大的不同的什么，底层是如何实现的？

            ai结合整理的知识点生成

            其实白屏的本质,就是用户从发出请求,到眼睛里第一次看到有内容的页面,中间这段「什么都看不到」的时间。那 CSR 和 SSR 最大的区别,就在于这段等待里到底塞了多少步骤。SSR 之所以能缩短白屏,核心就一句话:它把「首屏内容」这件事,从浏览器挪到了服务端提前做完了。

            第一层·为什么白屏更短？

            我们先看 CSR 的链路。浏览器请求一个 URL,服务器先甩回来一个基本是空壳的 HTML,里面就一个 <div id="app">。这时候页面是白的。然后浏览器得去下载 JS、解析执行 JS,JS 跑起来之后再去调后端接口要数据,数据回来了才开始渲染 DOM。所以 CSR 的白屏时间大概等于:网络请求 + JS 下载 + JS 执行 + 接口请求 + 渲染,是一条串行的、很长的瀑布。应用越复杂、JS 越大,这个白屏就越久。

            那 SSR 呢?浏览器请求 URL,是前端的 Node 服务直接去把数据取好、在服务端就把带数据的完整 HTML 拼出来,一次性返回。浏览器拿到的不是空壳,而是已经有内容的 HTML,解析完直接就能画出来。这时候 JS 还没加载完也没关系,用户已经先看到页面了。

            所以关键差别是:CSR 是「等 JS 和数据都齐了才给看」,SSR 是「内容先给看,JS 慢慢在后台补」。 白屏自然就短了。

            第二层·跟 CSR 最本质的不同

            第一,首屏内容的产出方不一样。CSR 的首屏是浏览器端 JS 跑出来的;SSR 的首屏是服务端直出的 HTML 字符串。

            第二,也是更底层的——它缩短的是「请求数据的路径」。CSR 必须先把空 HTML 返回给浏览器,再由浏览器发起第二趟请求去要数据,这是两个来回。SSR 是前端服务器离后端更近,直接在服务端把数据取好拼进 HTML,少了「浏览器→拿到壳→再发数据请求」这一整个往返。这也是为什么 SSR 对低带宽、弱网用户体验提升特别明显。

            当然顺带的收益还有 SEO,因为爬虫不等你 Ajax,SSR 返回的 HTML 本身就是有内容的,利于抓取和索引。

            第三层·底层怎么实现

            底层我用一个词概括:同构(isomorphic),就是同一套代码,在服务端跑一遍、在浏览器又跑一遍。服务端负责把页面结构渲染出来,浏览器端负责把事件绑定「激活」上去。

            具体拆成几个环节:

            一是编译阶段。 一套代码会打包成两个 bundle,两个入口——entry-server 和 entry-client。服务端那份不需要编译 CSS、不需要 code split,因为 Node 一次性加载进内存反而更快;客户端那份会生成一个资源清单 client-manifest,告诉服务端这个页面该注入哪些 JS 和 CSS 标签。

            二是渲染阶段。 服务端用 createBundleRenderer 创建一个渲染器,用户请求进来时调 renderToString,把 Vue/React 组件递归转成 vnode,再拼成 HTML 字符串。数据怎么来?组件上会定义一个预取数据的方法——Vue 里叫 asyncData,它在实例化之前就执行,所以拿不到 this,得把 store 和路由当参数传进去。服务端先把这些数据全取好,塞给渲染器的上下文。

            三是最关键的「注水」和「脱水」。 服务端渲染完,会把这次用到的状态数据序列化,塞到 HTML 里的 window.__INITIAL_STATE__,这叫注水;浏览器端 JS 启动的时候,再把这个全局变量读出来,通过 store.replaceState 同步回客户端的 store,这叫脱水。这一步是为了保证两端的数据状态完全一致,否则会出现服务端渲染的和客户端对不上的问题。

            四是激活,也就是 hydration。 服务器已经把 HTML 画好了,浏览器没必要把 DOM 全删了重建。所以 Vue 在 $mount 的时候会检查根节点有没有 data-server-rendered 这个属性,有的话就跳过重新渲染,只在现有的静态 DOM 上把事件监听绑定上去,让这个静态页面「活」过来,能响应后续交互。从这之后,路由跳转、交互就全在客户端跑了。

            SSR 把渲染和数据 IO 的压力从浏览器挪到了 Node 服务,高并发下服务器 CPU 和负载会上来,所以落地时我会特别注意几件事:一是加缓存,页面级或片段级缓存,相同请求直接返回别重复渲染;二是只渲染首屏,比如列表一屏看得见五条就只服务端渲五条,剩下的客户端异步补;三是严格控制服务端接口的超时时间,防止后端抖动把 Node 服务拖垮;四是要有降级方案,SSR 挂了能退回 CSR,保证可用性。

            那在渲染阶段，服务端拼接好的html字符串是已经用asyncData获取到的数据更新之后的，还是等到客户端激活的时候再更新的？

            用户请求进来,服务端不是直接就 renderToString,而是有一个数据预取阶段：

            1. 逐个调用组件上的静态方法 asyncData(React 生态里是 loadData);
            2. asyncData 把数据写入 store(它是同步 await 完才继续的);
            3. 等到所有 asyncData 都 Promise resolve、store 填好了,才调用 renderToString 开始渲染组件。

            store 有数据了,组件渲染出的 vnode 转成 HTML 字符串,此时 、 这些插值已经被替换成真实值了。然后渲染完顺手把这份 state 序列化,塞进 window.__INITIAL_STATE__ 一起吐给浏览器,叫注水。

            所以浏览器拿到的 HTML 里,<div></div> 已经是 <div>3</div> 这种成品,连"数据放哪了"都告诉你了——就在 window.__INITIAL_STATE__ 里。

            客户端激活时不做数据更新,只是把注进来的 state 读回 store,并在现成的 DOM 上绑事件：

            1. 先把 window.__INITIAL_STATE__ 通过 store.replaceState 同步进客户端 store,这叫脱水，保证两端状态一致;
            2. $mount 时检测到 data-server-rendered 属性,跳过重新渲染,直接在现成的 DOM 上绑定事件监听——这就是 hydration;
            3. 在 componentDidMount 里 if (!this.props.list.length) 的判断,意思就是:首屏组件已经有服务端给的数据了,就不再发一次请求;只有当路由跳转后新挂载的组件、store 里没有它的数据时,才由客户端自己去拉。

            那客户端激活时万一数据和服务端不一致怎么办?

            这正是 hydration 的意义所在,React 18 里叫 hydrateRoot,Vue 就是查 data-server-rendered;一旦检测到两端不一致,框架会放弃激活、客户端重新渲染做兜底,代价是首屏会闪一下(React 会先警告再重渲)。所以正常流程必须保证"服务端渲染用的数据 = 注入的 state = 客户端同步的 state"三者严格一致,这也是为什么 asyncData 必须在组件实例化前执行、不能访问 this——它就是为了保证这个一致性而设计的。

            先统计人工审核打回 AI 代码的原因，归成五类：业务逻辑错、不符合项目已有约定比如重复造轮子、过度设计改动越界、UI 的加载失败空数据三态不全、还有幻觉，就是调用了不存在的接口字段或组件。

            三态缺失是 AI 代码的高频问题，但人工审核又最容易看漏。代码评审擅长发现"写错的代码"，不擅长发现"没写的代码"。

            异步数据的三种非正常状态：加载中（loading）、请求失败（error）、请求成功但数据为空（empty）。"三态缺失"就是 AI 只写了"数据正常返回"那一条路径，另外三条漏了。

            第一件，把需求前置成一份变更契约。

            让 AI 写代码之前，人先花五分钟写清楚四件事：目标、允许改哪些文件、必须复用哪些已有组件、以及两三条可以点击验证的验收点。

            一是"必须复用 ProTable、必须走封装的 request 层"这种信息，AI 不是写得差，是我们根本没告诉它。二是允许改哪些文件写死了，那"改动越界"就从人工判断变成了机器判断，CI 直接比对 diff 文件列表超不超范围。

            第二件，把语义约束翻译成类型约束。

            凡是能让 tsc 报错的约定，就不要写进规范文档，也不要写进评审清单，因为写了没人看。

            举个具体例子。三态检测不了，那我们就封一个 AsyncBoundary 容器，把 empty 这个 prop 设成必填。漏写空态，TypeScript 直接编译不过。

            这样"你要记得写空态"这条靠自觉的规范，就变成了一条编译错误。幻觉类也是同一个思路，用 OpenAPI 生成 TS 类型。

            第三件，CI 门禁。

            这是存量项目的生死线。我们加了类型检查、ESLint、type-coverage 量化 any 比例、jscpd 查重复率、dependency-cruiser 查分层依赖，还有 danger 查改动范围和 diff 规模。

            # 如何标准量化？

            第一层准入指标，是硬门禁

            CI 全绿、契约完整、改动范围合规、单次改动规模不超标。全是布尔判定，任何一个不过就合不进去。

            • CI 全绿：iCode 流水线里按固定顺序加这几个 job，前面的挂了后面不跑；类型检查、eslint、any渗透、重复率、死代码

            存量代码全部只卡变更行、只卡新增。没有这条，这套门禁第一天就全红，团队第三天就绕过它了。

            • 契约完整：iCode 的 MR 描述就是契约载体，用 danger 脚本做机器校验（danger 14.x 的 GitLab DSL 原生支持 MR 描述读取）：
            // dangerfile.ts
// 读 MR 描述
const contract = danger.github?.pr?.body ?? danger.gitlab?.mr?.description ?? '';

const requiredSections = ['目标', '允许改动范围', '必须复用', '验收点'];
const missing = requiredSections.filter((s) => !contract.includes(s));

// 验收点至少 2 条
const acceptanceCount = (contract.match(/^\s*(?:-|\d+\.)\s+/gm) ?? [])
  .filter((line) => /能|看到|返回|跳转|点击/.test(line)).length;

if (missing.length) {
  fail(`变更契约缺失：${missing.join('、')}，请先填写 L0 变更契约再提交评审。`);
}
if (acceptanceCount < 2) {
  warn('验收点少于 2 条，建议至少 2 条可点击验证的验收点。');
}

            danger.js 是一个跑在 CI 里的 MR 校验框架，只支持 GitHub 和 GitLab 两家平台的 MR/PR；也可以单独写一个脚本 check-contract.ts 实现校验逻辑

            • 改动范围合规：这也是 danger 做：解析契约里的文件声明，和本次 MR 实际改动文件做比对。

            当初为什么坚决把这条做硬：AI 在长对话里最容易夹带无关改动——你让它改列表页筛选，它顺手把共用 request 层重构了，还改了三个看着"顺手"的文件。这恰恰是"过度设计/改动越界"那一类的机器化表达。

            这里有个诚实的边界："超出范围但合理"的情况是存在的，比如改着改着发现必须动一个公共组件。所以配套规则是：可以超，但必须回到契约里显式声明"我为什么要动它"，等于把一次静默越界变成一次显式决策。给流程留了理性出口，人才不会想绕过它。

            • 单次改动规模 ≤ 400 行：danger 里 git.diff 统计变更行数，超了直接 fail：
            const additions = danger.git.diff?.split('\n').filter((l) => l.startsWith('+')).length ?? 0;
if (additions > 400) {
  fail(`本次改动新增 ${additions} 行，超过 400 行，请拆分后分别评审合入。`);
}

            AI 生成的大 diff 里，夹带无关修改的概率随行数急剧上升，机器能查文件范围，查不出"同一行里混了两件事"；二是评审有效性在 diff 变大后断崖下降，超过一定量级人基本只能扫着看。所以宁可强制拆分，让每次评审都只处理一个完整、可理解的事。

            开发把契约写进 MR 描述 → 流水线跑 CI（全绿）→ danger 校验契约完整性和文件范围 → 规模检查 → 机器门禁全过，才轮到人工，人工只看那五条机器看不了的。准入指标的目的是把评审人的注意力从"检查语法和范围"里解放出来，全部留给真正的业务判断。

            第二层过程指标，衡量 AI 输出质量，用来反向迭代我们的 skill 和 prompt。

            最关键的一个叫人工修改率：合入前人工改了多少行，除以 AI 生成了多少行。做法是让 AI 的产出先单独一个 commit，commit 打上 AI-Assisted 的 trailer，人工修改另开一个 commit，脚本按 trailer 分组统计。这个数字直接量化了"AI 写的离能上线还差多远"，而且能按 skill 版本做 A/B 对比。

            第三层结果指标，衡量是不是真达到生产标准。

            十四天返工率：一次改动合入后十四天内，有多少行被改掉或删掉。选它的理由：纯 git 脚本就能算，不依赖任何新基建；最重要的是,它同时反映逻辑错误和过度设计,因为写错了要改,过度抽象后来也要拆。

            还有一点我想强调,只看前两层是危险的。返工轮次降了、审核快了,只能说明审核成本降了。必须同时看第三层不恶化,否则这套东西就变成"更快地合入更差的代码"。

            明确踩过或者避开的坑：

            1. 不要用开发者的主观感受当指标
            2. 不要指望 AI 自查兜住逻辑错误。 有篇 ICLR 的论文结论很明确，在没有外部正确性信号的情况下，模型自我纠错往往越改越差；一旦给它外部判定信号，比如编译器、测试、静态检查，才稳定有效。所以我们的资源分配是：前置契约大于机器门禁，机器门禁大于 AI 自查。
            3. LLM 打的分不能当门禁。 它有很明确的 verbosity bias，写得长的容易得高分，那正好奖励了过度设计。我们只用它做同一套 rubric 下两个 skill 版本的相对比较，不看绝对分。

            ‌“verbosity bias”通常译为“冗长偏差”‌，指评估者（尤其是大模型作为裁判时）倾向于给更长、更啰嗦的回答打高分，即使这些回答信息密度低或包含无关内容

            # 你们这套工程上线后有哪些收益呢？提效多少呢？

            收益我分三类讲：一类是结构性的，不需要统计就能证明；一类是过程指标，有数据但有前提；还有一类是我不敢给精确数字的，我也说清楚为什么。

            先说第一类，我觉得这是最实在的收益：有三类缺陷在上线后是被结构性消除的，不是概率性降低。

            幻觉类，就是调用不存在的接口字段，现在它编译不过。三态缺失，因为 empty 变成了必填 prop，漏写同样编译不过。改动越界，CI 直接比对 diff 文件列表，超出契约范围就卡住。

            第二类是过程指标，试点四周的数据：AI 改动的首次门禁通过率【填 50% → 85%】，人工 CR 返工轮次从【填平均 3 轮降到 1 轮】，人工修改率，就是合入前人工改的行数除以 AI 生成行数，从【填 40% 降到 10%】。

            第三类，也是我想主动说明的：整体提效百分之多少，我不敢给一个精确数字。 原因有三个。

            一，我们没有真正的对照组。同一批人、同一个迭代，不可能既用这套流程又不用。

            二，同期有混杂变量。团队对 AI 工具的熟练度本身在涨，需求复杂度每个迭代也不一样，这些都会污染数字。

            三，更关键的是，主观感受在这件事上是不可靠的。 METR 有个随机对照实验，十六个资深开源开发者、两百多个真实 issue，结果是用 AI 之后实际耗时增加了百分之十九，但开发者事后仍然认为自己被加速了百分之二十。所以如果我给你一个"团队感觉快了百分之三十"，那基本没有信息量。

            这套东西我们是分阶段上的，目前基线采集跑完了，门禁刚转成强制，所以完整的前后对比数据还不够一个有说服力的样本量。

            我特意把基线采集放在第一周、不加任何限制，就是因为我见过太多"上了一堆工具，但说不清到底有没有变好"的情况。没有基线，后面所有提质提效的说法都是故事。

            # 基线采集和 门禁转为强制 是什么意思，具体怎么操作的呢？

            *"基线采集"是动手改任何东西之前，先把现状数字记下来；"门禁转为强制"*是规则上线的方式——先只报错不卡死，数据验证阈值合理了，再改成真拦。

            基线采集：

            第一周唯一任务是把"改动之前"的数字记死，之后每一步都能跟它对比。

            1. 类型覆盖率（any 渗透率）:
            npx type-coverage --detail            # 输出当前百分比 + 逐文件明细
            1. 代码重复率:
            npx jscpd src --reporters json --output .jscpd-baseline.json   # 生成基线文件，入库
            1. 死代码 / 未用导出 / 未声明依赖
            npx knip                          # 输出 issue 列表和总数
npx knip --max-issues 87          # 把 87 设为当前值——以后只许降不许涨
            1. 14 天返工率（churn）——纯 git 脚本算，不用任何工具。口径：合入时新增的行，在合入后 14 天内被修改或删除的比例。
            # 第一步：列出过去 8 周合入主干的 commit 及各自新增行数
git log origin/main --since="8 weeks ago" --pretty="%H %ad" --stat

# 第二步：对每个 commit，看它合入 14 天后，新增的行有多少被动过
# 用 git log -L 追踪行级历史：
git log -L <start>,<end>:<file> --since=<merge_date> --until=<merge_date + 14 days>

            统计口径是"新增行集合中，14 天内被触碰过的占比"

            1. 历史 CR 的返工数据（从 iCode/git 拉）：
            git rev-list --count origin/main..feature/xxx   # 分支上 commit 数 - 1 ≈ 返工轮次

            指标 基线值 采集方式 类型覆盖率 91.2% type-coverage 存量重复率 6.8% jscpd baseline 文件 knip issue 数 87 knip --max-issues 14 天返工率 待算 git 脚本 平均返工轮次 2.3 轮 iCode 历史 CR

            门禁转为强制：先 warn 后 error 的三周节奏

            规则不是一次性砸下去的，砸下去那天如果全红，团队第三天就会绕过你。

            1. 全部以 warn 上线，只报不卡。
            # ESLint：本地/开发环境规则全部设 warn
# 配置文件里：
rules: {
  'no-restricted-imports': 'warn',
  '@typescript-eslint/no-unsafe-member-access': 'warn',
  // ...
}

            这周 CI 里 warn 不失败，但报告要留档。目的是回答一个问题："如果这些规则转成 error，会卡掉多少正常改动？" 如果 warn 命中率里有一大半是误报，说明规则写错了，先修规则；如果命中率都集中在真正的问题上，说明阈值合理，可以转强制。

            1. 转 error，只对新增生效，存量不追溯。
            • 方式一：只检查变更文件（推荐，天然棘轮）。 用 lint-staged 在 CI 里只对本次 MR 改动的文件跑 lint + --fix：
            # package.json
"lint-staged": {
  "*.{ts,tsx}": ["eslint --fix", "prettier --write"]
}
            • 方式二：绝对阈值类指标用"基线 + 只许变好"；比如死代码超过87就失败，类型覆盖率低于91.2%就失败

            "转为强制"落地在 CI 上的样子：

            quality-gate:
  script:
    - npx tsc --noEmit
    - npx eslint . --max-warnings 0          # CI 环境用 max-warnings 0 = warn 也当失败
    - npx jscpd src --baseline .jscpd-baseline.json --fail-on-new-clones  # # 新增克隆 → 失败
    - npx knip --max-issues 87  # 超过 87 → 失败
    - npx type-coverage --at-least 91.2 --history-file  # 低于基线 → 失败
    - npx dependency-cruiser --exit-code
    - npx danger ci                          # 契约完整性 + 改动范围 + 规模
  when: manual                            # 初期挂在"人工可跳过"位，两周后 required

            --max-warnings 0 让本地是 warn、CI 是 error——开发体验和门禁强度分离；when: manual 一开始留个口子，稳定后再改 required，这叫"软转强制"，第 4 周才完全卡死。

            # 支付链路的单测如何设计？

            B 端前端里的支付链路，风险不在"渲染"，在这三件事：

            • 幂等：用户连点两次"确认支付" → 产生两个支付单
            • 轮询状态机：支付成功后页面还在轮询、或者轮询永远停不下来
            • 后端返回未知状态：后端加了个你没见过的状态码，前端静默放行，用户看到"支付中"其实是已关闭

            设计原则（三条，资深感在这）

            1. 测试的是状态机和契约，不是 UI 渲染。 页面长什么样不值得测，状态转错了会出事。
            2. 把可测逻辑全部抽成纯函数，hook 只剩胶水。 这样 80% 的用例是纯函数测试：不需要 DOM、不需要 mock 网络、毫秒级跑完。
            3. 每个用例对应一次真实线上事故，不为覆盖率写。 这是"bug 驱动用例"：线上出过"连点两次导致双支付单"，就把这条写进用例，保证它不会再发生。

            # 上面的提前写契约，之后强制校验契约式如何实现的？

            落地链路：契约模板（文档）→ 校验脚本（代码）→ 接入点（hook + CI）

            第一步：契约模板（填好你这个项目的版本）

            ## 变更契约
- 目标：一句话说清要做什么（例：run 执行中模型调用失败时增加 2 次重试并埋点）

- 允许改动范围（写目录前缀）：
  - server/src/agent/          # 运行时/状态机
  - server/src/skills/         # skill 注册
  - server/src/routes/         # HTTP 路由
  - web/app/                   # 前端页面

- 必须复用：
  - AgentRuntime / applyTransition（状态流转不许自己另写一套）
  - EventEmitter + stream（事件/审计必须走它，不许 console.log 代替）
  - lintDraft（guard/linter.ts，草稿敏感词拦截）
  - skills/registry.ts（新 skill 必须注册，不许散落）
  - db/repositories/*（routes 里不许裸写 SQL / 直连 pg）

- 禁止：
  - 绕过 server/src/models/ 直连 LLM SDK
  - 改 db schema 不更新 migrate
  - 新增 npm 依赖（需显式声明理由）
  - 改动 server/src/analytics/（口径变更需单列 CR）

- 验收点（必须可执行）：
  1. pnpm --filter @cs-agent/server typecheck 通过
  2. pnpm --filter @cs-agent/server test 全绿（涉及 runtime/state-machine 必须）
  3. pnpm validate:happy-path 跑通（全 mock 端到端）
  4. 前端改动：pnpm --filter @cs-agent/web build 通过

            第二步：校验脚本

            #!/usr/bin/env tsx
/**
 * L0 变更契约校验器
 * 本地：读 .cr-contract.md；CI：读 $CR_CONTRACT 环境变量（CR 描述注入）。
 * 通过返回 0，失败返回 1。
 */
import { execSync } from 'node:child_process';
import { readFileSync, existsSync } from 'node:fs';

const [PASS, FAIL, WARN] = ['\x1b[32m[PASS]\x1b[0m', '\x1b[31m[FAIL]\x1b[0m', '\x1b[33m[WARN]\x1b[0m'];
const baseIdx = process.argv.indexOf('--base');
const base = baseIdx >= 0 ? process.argv[baseIdx + 1] : 'origin/main';

// 1. 读契约：环境变量 > 本地文件
const md = process.env.CR_CONTRACT ?? (existsSync('.cr-contract.md') ? readFileSync('.cr-contract.md', 'utf8') : '');

// 2. 解析小节（markdown 结构）
function section(title: string): string {
  const m = md.match(new RegExp(`^##\\s*${title}\\s*$([\\s\\S]*?)(?=^##\\s|$)`, 'm'));
  return m?.[1]?.trim() ?? '';
}
const goal = section('目标');
const scope = section('允许改动范围').split(/\r?\n/).filter(Boolean).map((l) => l.replace(/^[-*]\s*/, '').trim()).filter(Boolean);
const reuse = section('必须复用').split(/\r?\n/).filter(Boolean);
const accept = section('验收点').split(/\r?\n/).filter(Boolean);

// 3. 契约完整性
const failures: string[] = [];
if (!goal) failures.push('缺少【目标】');
if (!scope.length) failures.push('缺少【允许改动范围】');
if (accept.length < 2) failures.push('【验收点】少于 2 条');
if (accept.length >= 2 && !accept.some((l) => /\b(pnpm|npm|yarn)\s/.test(l)))
  console.log(`${WARN} 验收点没有可执行命令，建议写成 pnpm xxx（可自动跑）`);

// 4. 改动范围 vs diff（范围按目录前缀匹配）
const changed = execSync(`git diff --name-only ${base}...HEAD`, { encoding: 'utf8' })
  .split('\n').map((l) => l.trim()).filter(Boolean);
const outOfScope = changed.filter((f) => !scope.some((g) => f.startsWith(g)));
if (outOfScope.length) failures.push(`改动超出契约范围：${outOfScope.join(', ')}`);

// 5. 规模
const additions = execSync(`git diff --numstat ${base}...HEAD`, { encoding: 'utf8' })
  .split('\n').filter(Boolean)
  .reduce((sum, l) => sum + parseInt(l.split('\t')[0] ?? '0', 10), 0);
if (additions > 400) failures.push(`新增 ${additions} 行，超过 400 行，请拆分`);

// 6. AI 标记（分组统计用）
